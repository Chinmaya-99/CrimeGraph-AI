# SIH26189 — AI-Powered Criminal Network Analysis System

**Core idea:**
Start with a seed investigation, such as an FIR. Extract entities from it, correlate those entities against multiple data sources, discover relationships, build a graph, identify suspicious/high-priority nodes, and recursively expand the network to uncover deeper connections. Use blockchain/security for **tamper-evident provenance and auditability**, not for storing the actual sensitive data.

# 3. AI Extraction Engine

From the FIR or other unstructured source, extract entities such as:

```text
PERSON
PHONE
LOCATION
VEHICLE
ORGANIZATION
ACCOUNT
CASE
EVENT
```

Example:

> Rahul met Arjun near Bhubaneswar using vehicle OD02AB1234.

becomes:

```text
PERSON: Rahul
PERSON: Arjun
LOCATION: Bhubaneswar
VEHICLE: OD02AB1234
```

We can use NER models such as spaCy/transformers for entity extraction.

---

# 4. Relationship Extraction

Extract relationships from the same source.

Example:

```text
Rahul ──met──> Arjun
Rahul ──used──> Vehicle X
Arjun ──located_at──> Location Y
```

Every relationship should retain:

```text
relationship_type
source
timestamp
confidence
evidence
```

Important: the LLM should **not blindly invent relationships**. The relationship should be backed by an evidence span from the source.

# 7. Relationship Graph

All resolved entities and relationships are represented in **Neo4j**.

Example:

```text
             Rahul
           /   |    \
       calls  owns  seen_at
        /      |       \
     Arjun   Vehicle   Location
       |
     calls
       |
       D
```

The graph stores:

```text
Nodes
Edges
Relationship types
Timestamps
Source
Confidence
Evidence
```

### Database split

Rather than running six separate database servers:

```text
PostgreSQL
│
├── fir_records
├── contact_records
├── bank_records
├── social_records
├── criminal_history
└── surveillance_records
```

and:

```text
Neo4j
└── Intelligence Graph
```

So:

**PostgreSQL = source data**

**Neo4j = relationship intelligence**

# 8. Network Intelligence Engine

Once the graph exists, analyze it.

### Key-influencer detection

Use graph metrics such as:

```text
PageRank
Betweenness Centrality
Degree Centrality
Community structure
```

to identify important nodes.

Example:

```text
Person A
17 connections
3 communities
high betweenness
high transaction activity

→ High-priority node
```

The system should describe this as an **analytical priority**, not declare someone guilty.

# 9. Suspicious Pattern & Anomaly Detection

Look for patterns such as:

```text
Repeated calls
Communication bursts
Unusual financial activity
Multiple connections across communities
Shared locations
Sudden network expansion
Temporal coordination
Unusual transaction behavior
```

The initial MVP can use rule/statistical scoring.

Later, ML-based anomaly detection can be added.

Output:

```text
Anomaly Score: 0.91
```

not:

```text
Person is criminal
```

# 10. Multi-Hop Network Expansion

This is one of our **main differentiating features**.

Suppose the initial network is:

```text
A → B → C
A → D
C → D
```

Even though D wasn't in the initial FIR, D has multiple paths into the network.

The system detects:

```text
A → D
A → B → C → D
```

and increases D's investigation priority.

### Recursive process

```text
Seed entities
      ↓
1-hop expansion
      ↓
Score connected entities
      ↓
Top-N candidates
      ↓
2-hop expansion
      ↓
Recalculate scores
      ↓
3-hop expansion
      ↓
Final network
```

We can start with **Top 3** high-priority entities and expand them to a configurable depth, such as 2–3 hops.

This prevents the graph from exploding across the entire dataset.

# 14. Evidence & Explainability

Every important relationship and alert needs an evidence trail.

Example:

```text

Evidence
──────────────
Transactions: 5
Total amount: ₹X
First observed: XX/XX/XXXX
Last observed: XX/XX/XXXX

```

For a multi-hop relationship:

```text

A → B → D

Path 2:
A → C → D
```

The investigator can see exactly **why D was surfaced**.

# 15. Blockchain / Tamper-Evident Layer

This is how we address the official **Blockchain & Cybersecurity** theme without doing a pointless “blockchain database.”

We **do not store sensitive FIR/CDR/bank data directly on-chain**.

Instead:

```text
Source Record
      ↓
Canonical representation
      ↓
SHA-256 hash
      ↓
Tamper-evident ledger
```

Record audit events such as:

```text
DATA_INGESTED
ENTITY_CREATED
ENTITY_MERGED
RELATION_CREATED
ANALYSIS_EXECUTED
REPORT_GENERATED
INVESTIGATOR_ACCESSED_RECORD
```

If a stored record changes:

```text
Current Hash ≠ Recorded Hash
             ↓
       TAMPER DETECTED
```

This gives us **data integrity + provenance + auditability**.

## What makes our concept different

The core isn't simply:

**“AI finds criminals.”**

It is:

> **A secure, explainable intelligence platform that starts from a known investigation, correlates fragmented data across multiple sources, discovers multi-hop relationships, identifies high-priority network entities, and provides evidence-backed investigative leads with tamper-evident provenance.**
